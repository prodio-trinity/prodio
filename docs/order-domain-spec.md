# Order 도메인 기능 명세서

## 1. 문서 목적

이 문서는 Prodio의 Order 도메인이 제공하는 수주 등록·관리 기능과 업무 규칙, 데이터 소유권, 외부 도메인 연동 계약을 정의한다.

- 기준일: 2026-08-24
- 대상 사용자: 거래처(`CLIENT`), 관리자(`ADMIN`)
- 대상 범위: 백엔드 `com.prodio.order`, 프런트엔드 `features/orders`

## 2. 도메인 책임과 경계

Order 도메인은 거래처가 요청한 주문을 접수하고, 입금 확인 전까지 주문 내용을 관리하며, 주문 확정 또는 취소 결과를 기록한다.

### Order가 소유하는 정보

- 주문 식별자와 주문서명
- 주문 시점의 거래처명·거래처 연락처 스냅샷
- 주문 품목, 수량, 품목명·단가 스냅샷
- 부가세 포함 여부와 최종 주문 금액
- 주문 시점의 배송 정보 스냅샷
- 거래처별 주문용 저장 배송지
- 주문 메모
- 주문 상태와 취소 사유
- 등록자, 등록 시각, 최종 수정 시각

### 다른 도메인이 소유하는 정보

- 계정과 권한: User 도메인
- 거래처 원본 정보, 품목 원본 정보, 카테고리와 현재 단가: Catalog 도메인
- 생산 시작·진행·완료: Production 도메인
- 출고·배송 진행 및 완료: 해당 생산·배송 도메인
- 통계용 조회 모델: Statistics 도메인

Order는 다른 도메인의 테이블이나 Repository를 직접 조회하지 않는다. 공개 인터페이스 또는 공개 이벤트로만 통신한다.

## 3. 사용자 역할

### 거래처(`CLIENT`)

- 로그인 계정과 1:1로 연결된 거래처 정보 확인
- 자신의 거래처 명의로 주문 등록
- 자신의 거래처 주문 목록과 상세 조회
- 입금 대기 주문 수정
- 입금 대기 주문 취소
- 거래처 주문용 배송지 등록·수정·삭제

거래처는 요청의 `clientId`를 임의로 변경할 수 없다. 서버가 로그인 계정에 연결된 거래처를 다시 확인한다.

### 관리자(`ADMIN`)

- 전체 거래처의 주문 목록과 상세 조회
- 상태·검색어 기반 주문 검색
- 입금 대기 주문 내용 수정
- 입금 확인 후 주문 확정
- 입금 대기 주문 취소
- 필요한 거래처의 배송지 관리

관리자 수주 관리 화면은 접수된 주문의 확인과 처리 기능에 집중하며 새 주문 등록 버튼은 표시하지 않는다.

## 4. 주문 상태와 생애주기

| 상태 | 화면 표시 | 의미 |
|---|---|---|
| `PENDING_PAYMENT` | 입금 대기 | 주문이 접수되어 수정·확정·취소할 수 있는 상태 |
| `CONFIRMED` | 주문 확정 | 관리자가 입금을 확인하여 주문이 확정된 상태 |
| `CANCELLED` | 주문 취소 | 주문이 취소되어 더 이상 변경할 수 없는 상태 |

상태 전이는 다음과 같다.

```text
주문 등록
   │
   ▼
PENDING_PAYMENT ── 입금 확인 ──▶ CONFIRMED
   │
   └──────── 취소 ─────────────▶ CANCELLED
```

### 상태 규칙

- 신규 주문은 항상 `PENDING_PAYMENT`로 생성한다.
- 주문 내용 수정은 `PENDING_PAYMENT`에서만 허용한다.
- 주문 확정은 `PENDING_PAYMENT`에서만 허용한다.
- 주문 취소는 `PENDING_PAYMENT`에서만 허용한다.
- 주문 취소 시 취소 사유는 필수다.
- `CONFIRMED`와 `CANCELLED`는 종결 상태이며 Order에서 다시 변경하지 않는다.
- 생산 및 배송 상태를 Order 상태에 추가하지 않는다.

## 5. 주문 등록

### 5.1 거래처 확인

1. 서버가 로그인 계정 ID로 Catalog 공개 계약을 호출한다.
2. 활성 상태인 연결 거래처를 확인한다.
3. 연결 거래처가 없으면 주문 등록을 허용하지 않는다.
4. 거래처 원본 정보는 Catalog가 소유하고 Order에는 주문 시점 스냅샷만 저장한다.

주문 화면에 표시하는 거래처 정보는 다음과 같다.

- 거래처 코드
- 회사명
- 대표자명
- 담당자명
- 사업자등록번호
- 거래처 연락처
- 사업장 위치

### 5.2 품목 선택

- 카테고리와 품목 정보는 Catalog가 제공한다.
- 대분류·소분류를 선택하여 해당 분류의 활성 품목을 조회할 수 있다.
- 품목명 또는 품목코드로 검색할 수 있다.
- 주문 한 건에 여러 품목을 추가할 수 있다.
- 같은 품목을 중복 행으로 추가하지 않고 기존 품목의 수량을 증가시킨다.
- 각 품목의 수량은 1 이상의 정수다.
- 최종 주문 요청은 품목 ID와 수량을 전달한다.

서버는 요청받은 화면 단가를 신뢰하지 않는다. 저장 직전에 Catalog 공개 계약으로 활성 품목과 현재 단가를 다시 조회한다.

### 5.3 주문서명

- 주문서명은 선택 입력이며 최대 200자다.
- 입력한 경우 목록과 상세 화면에서 주문을 구분하는 대표 이름으로 사용한다.
- 입력하지 않은 경우 일부 품목명을 조합하여 화면에 표시한다.

### 5.4 금액 계산

품목별 금액은 다음과 같이 계산한다.

```text
품목별 금액 = 주문 시점 단가 × 수량
공급가액 = 모든 품목별 금액의 합계
최종 금액 = 부가세 포함 선택 시 공급가액 × 1.1
```

- 금액 단위는 원 단위 정수다.
- 부가세 계산 결과는 반올림하여 원 단위로 저장한다.
- 최종 금액은 서버가 다시 계산한다.
- 음수 금액과 계산 범위를 초과한 금액은 허용하지 않는다.

### 5.5 메모

- 생산 또는 납품 시 참고할 주문 메모를 선택 입력할 수 있다.
- 최대 길이는 2,000자다.

## 6. 배송 정보

주문 등록과 수정에는 배송 정보가 반드시 필요하다.

### 배송지 선택 방식

- 본사: Catalog 거래처의 기본 사업장 주소 사용
- 최근 배송지: 해당 거래처의 최근 주문 배송 스냅샷 사용
- 저장 배송지: Order가 관리하는 거래처별 배송지 사용
- 새 배송지: 배송지 관리 화면에서 등록 후 선택

### 저장 배송지 관리

- 배송지명
- 받는 사람
- 배송 연락처
- 우편번호
- 기본 주소
- 상세 주소

거래처는 자신의 거래처 배송지만 조회·등록·수정·삭제할 수 있다. 관리자는 업무 대상 거래처의 배송지를 관리할 수 있다.

국내 주소 입력은 Daum 우편번호 서비스를 사용하며, 배송 연락처는 국내 전화번호 형식으로 표시한다.

### 주문 배송 스냅샷

주문에는 선택한 배송지의 다음 값을 복사하여 저장한다.

- 저장 배송지 ID(저장 배송지를 선택한 경우)
- 배송지명
- 받는 사람
- 배송 연락처
- 우편번호
- 기본 주소
- 상세 주소

저장 배송지 원본이 이후 수정되거나 삭제되어도 기존 주문의 배송 정보는 변경되지 않는다.

## 7. 견적서

- 품목을 하나 이상 선택하면 견적서 출력 기능을 사용할 수 있다.
- 견적서에는 거래처, 주문 품목, 수량, 단가, 품목별 금액, 부가세와 총금액을 표시한다.
- 견적서는 A4 비율의 화면으로 제공한다.
- 이미지(PNG) 저장과 인쇄를 지원한다.
- 브라우저 인쇄 기능을 통해 PDF로 저장할 수 있다.

견적서는 주문 작성 단계의 예상 금액을 확인하기 위한 화면 기능이며 별도 주문 상태를 만들지 않는다.

## 8. 주문 조회

### 관리자 주문 목록

- 전체 주문 수, 입금 대기 수, 주문 확정 수 표시
- 상태 필터: 전체, 입금 대기, 주문 확정, 주문 취소
- 거래처명 또는 품목명 검색
- 페이지 단위 조회
- 주문번호, 수주처·주문서명, 수량, 금액, 상태 표시
- 입금 대기 주문에만 상태 변경 기능 표시

### 거래처 내 주문 목록

- 로그인 계정에 연결된 거래처의 주문만 표시
- 전체 주문 수, 입금 대기 수, 주문 확정 수 표시
- 상태 및 검색어 필터
- 주문번호, 주문서명·품목, 수량, 주문 금액, 진행 상태 표시
- 입금 대기 주문에만 수정·취소 기능 표시

### 주문 상세

- 거래처와 주문서명
- 전체 품목, 수량, 주문 시점 단가와 품목별 금액
- 부가세 포함 여부와 총금액
- 주문 상태와 취소 사유
- 배송 스냅샷
- 주문 메모
- 등록자와 등록·수정 시각

거래처 상세 조회는 로그인 계정에 연결된 거래처 ID와 주문의 `client_id`가 일치해야 한다. 다른 거래처 주문은 존재 여부가 노출되지 않도록 조회 실패로 처리한다.

생산 및 납품 정보는 각 도메인의 공개 조회 계약 또는 조회 모델이 제공하는 경우에만 표시한다.

## 9. 주문 수정·확정·취소

### 주문 수정

- 거래처는 자신의 주문만 수정할 수 있다.
- 관리자는 업무 대상 주문을 수정할 수 있다.
- 거래처 자체는 변경할 수 없다.
- 주문서명, 품목·수량, 부가세 여부, 배송 정보와 메모를 변경할 수 있다.
- 서버는 품목 활성 여부와 단가를 다시 확인하고 총금액을 다시 계산한다.
- 수정 완료 후 `OrderUpdatedEvent`를 발행한다.

### 주문 확정

- 관리자만 수행한다.
- 입금 대기 주문에서만 가능하다.
- 확인 절차 후 상태를 `CONFIRMED`로 변경한다.
- 확정 완료 후 `OrderConfirmedEvent`를 발행한다.

### 주문 취소

- 관리자와 주문 소유 거래처가 수행할 수 있다.
- 입금 대기 주문에서만 가능하다.
- 취소 사유를 필수로 입력한다.
- 상태를 `CANCELLED`로 변경하고 취소 시각을 기록한다.
- 취소 완료 후 `OrderCancelledEvent`를 발행한다.

동시 변경을 방지하기 위해 수정·확정·취소 대상 주문은 잠금 조회 후 처리한다.

## 10. 공개 API

### 관리자 API

| 메서드 | 경로 | 기능 | 권한 |
|---|---|---|---|
| `GET` | `/api/orders` | 전체 주문 목록 조회 | `ADMIN` |
| `GET` | `/api/orders/{id}` | 주문 상세 조회 | `ADMIN` |
| `PUT` | `/api/orders/{id}` | 주문 내용 수정 | `ADMIN` |
| `PATCH` | `/api/orders/{id}/confirm` | 입금 확인 및 주문 확정 | `ADMIN` |
| `PATCH` | `/api/orders/{id}/cancel` | 주문 취소 | `ADMIN` |

### 거래처 API

| 메서드 | 경로 | 기능 | 권한 |
|---|---|---|---|
| `GET` | `/api/orders/mine` | 내 거래처 주문 목록 조회 | `CLIENT` |
| `GET` | `/api/orders/mine/{id}` | 내 거래처 주문 상세 조회 | `CLIENT` |
| `GET` | `/api/orders/client-context` | 로그인 계정의 거래처 정보 조회 | `CLIENT` |
| `PUT` | `/api/orders/mine/{id}` | 내 입금 대기 주문 수정 | `CLIENT` |
| `PATCH` | `/api/orders/mine/{id}/cancel` | 내 입금 대기 주문 취소 | `CLIENT` |

### 공통 주문 API

| 메서드 | 경로 | 기능 | 권한 |
|---|---|---|---|
| `GET` | `/api/orders/form-context` | 주문 작성용 거래처·품목 정보 조회 | `CLIENT`, `ADMIN` |
| `POST` | `/api/orders` | 주문 등록 | `CLIENT`, `ADMIN` |

관리자가 `form-context`를 조회할 때는 업무 대상 `clientId`를 지정할 수 있다. 거래처 사용자는 요청 값과 관계없이 로그인 계정에 연결된 거래처를 사용한다.

### 배송지 API

| 메서드 | 경로 | 기능 | 권한 |
|---|---|---|---|
| `GET` | `/api/orders/delivery?clientId={id}` | 본사·최근·저장 배송지 조회 | `CLIENT`, `ADMIN` |
| `POST` | `/api/orders/delivery/addresses` | 배송지 등록 | `CLIENT`, `ADMIN` |
| `PUT` | `/api/orders/delivery/addresses/{id}` | 배송지 수정 | `CLIENT`, `ADMIN` |
| `DELETE` | `/api/orders/delivery/addresses/{id}` | 배송지 삭제 | `CLIENT`, `ADMIN` |

모든 변경 API는 세션 인증과 CSRF 토큰 검증을 적용한다.

## 11. 주문 요청 데이터

```json
{
  "clientId": "10",
  "orderName": "8월 본사 설비 교체 주문",
  "items": [
    {
      "productId": "101",
      "quantity": 3
    },
    {
      "productId": "205",
      "quantity": 2
    }
  ],
  "vatIncluded": true,
  "delivery": {
    "addressId": "7",
    "name": "본사 창고",
    "recipientName": "홍길동",
    "recipientPhone": "010-1234-5678",
    "postalCode": "06236",
    "addressLine1": "서울특별시 강남구 테헤란로 123",
    "addressLine2": "1층 입고장"
  },
  "note": "도착 전 담당자에게 연락해 주세요."
}
```

거래처 주문에서는 서버가 로그인 계정과 연결된 거래처 ID를 사용한다. 품목명, 단가와 총금액은 클라이언트가 결정하지 않는다.

## 12. 도메인 이벤트

Order는 Spring의 `ApplicationEventPublisher`를 통해 모듈 공개 이벤트를 발행한다. 이벤트 발행은 주문 저장 트랜잭션 안에서 수행하며 Spring Modulith 이벤트 레지스트리를 통해 구독 처리를 관리한다.

### `OrderCreatedEvent`

주문 생성 후 발행한다.

- 주문 ID
- 거래처 ID·이름·연락처
- 주문서명
- 전체 주문 품목 스냅샷
- 부가세 포함 여부와 총금액
- 배송 스냅샷
- 메모
- 생성 시각

### `OrderUpdatedEvent`

주문 내용 수정 후 발행한다.

- 주문 ID
- 변경 후 전체 주문 스냅샷
- 수정 시각

### `OrderConfirmedEvent`

주문 확정 후 발행한다.

- 주문 ID
- 확정 시점의 전체 주문 스냅샷
- 생성 시각과 확정 시각

### `OrderCancelledEvent`

주문 취소 후 발행한다.

- 주문 ID
- 취소 사유
- 취소 시각

구독 모듈은 이벤트 클래스 자체를 기준으로 필요한 이벤트만 구독한다. Order는 구독 모듈의 테이블이나 처리 상태를 직접 관리하지 않는다.

## 13. 데이터 저장 구조

### `orders`

주문 Aggregate의 루트와 거래처·배송 스냅샷, 상태, 금액, 메모, 감사 정보를 저장한다. 기존 운영 테이블명을 유지한다.

### `order_items`

주문별 다중 품목을 저장한다.

- 주문 ID
- 표시 순서
- 품목 ID
- 품목명 스냅샷
- 단가 스냅샷
- 수량
- 품목별 금액

### `order_delivery_addresses`

거래처별 주문용 저장 배송지를 관리한다.

- 거래처 ID
- 배송지명
- 받는 사람과 연락처
- 우편번호와 주소
- 등록·수정 시각

Catalog 테이블과 물리적 외래 키를 만들지 않고 도메인 공개 계약으로 참조 유효성을 확인한다.

## 14. 스냅샷 정책

주문 이력은 주문 당시의 계약 사실을 보존해야 한다. 다음 원본 정보가 이후 변경되더라도 기존 주문은 변경하지 않는다.

- 거래처 회사명과 연락처
- 품목명과 단가
- 배송지명, 수령인, 배송 연락처와 전체 주소

주문 수정이 허용되는 입금 대기 상태에서 품목이나 배송 정보를 변경하면 수정 시점의 최신 값으로 주문 스냅샷을 다시 구성한다. 확정 또는 취소 이후에는 변경하지 않는다.

## 15. 검증 및 오류 조건

- 로그인 계정이 활성 사용자여야 한다.
- 거래처 주문은 로그인 계정과 활성 거래처가 연결되어야 한다.
- 주문 품목이 하나 이상이어야 한다.
- 동일 품목을 중복 행으로 저장할 수 없다.
- 모든 품목이 Catalog에 존재하고 활성 상태여야 한다.
- 수량은 1 이상의 정수여야 한다.
- 배송 정보와 기본 주소는 필수다.
- 저장 배송지를 선택하면 주문 거래처 소유의 배송지인지 확인한다.
- 주문 수정·확정·취소 시 현재 상태를 다시 검증한다.
- 거래처 조회·수정·취소는 주문의 거래처 소유권을 검증한다.
- 취소 사유는 공백일 수 없으며 최대 1,000자다.
- 페이지 번호는 0 이상, 페이지 크기는 1~100이다.

## 16. 인수 기준

- 거래처가 로그인하면 연결된 거래처 정보가 주문서에 자동 표시된다.
- 거래처가 없거나 비활성이면 주문을 등록할 수 없다.
- 카테고리 선택 또는 검색으로 활성 품목을 찾고 여러 품목과 수량을 입력할 수 있다.
- 서버 계산 금액과 화면 예상 금액이 일치한다.
- 본사·최근·저장 배송지를 선택하고 새 배송지를 관리할 수 있다.
- 주문 등록 후 상태가 `PENDING_PAYMENT`이고 생성 이벤트가 발행된다.
- 거래처는 자신의 입금 대기 주문만 수정·취소할 수 있다.
- 관리자는 입금 대기 주문을 확정하거나 취소할 수 있다.
- 수정·확정·취소마다 대응하는 이벤트가 발행된다.
- 확정·취소 주문은 수정하거나 다시 상태 변경할 수 없다.
- Catalog 원본이 변경되어도 기존 주문의 거래처·품목·배송 이력은 유지된다.
- 생산 및 배송 진행 상태는 Order 상태와 분리된다.
